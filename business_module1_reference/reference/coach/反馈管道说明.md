# 反馈管道（复盘链路）

> **V1.3 §2.1–2.5 的实现**。版本 B 的核心，也是把「训练」变成「训练 + 复盘」的闭环。
> 对应文件：`feedback_pipeline.py`（引擎）、`feedback_demo.py`（端到端演示）、`verify_feedback_pipeline.py`（自检）

---

## 0. 一句话

**训练产生记录，复盘产生差异，差异产生候选，候选经审核进题库。**

四环节：

```
① 复盘采集 DebriefRaw
      ↓
② 结构化观察 Observation
      ↓
③ 差异分析 CoverageMap + GapCandidate
      ↓
④ 审核与场景版本发布 ReviewCase → ScenarioVersion
```

---

## 1. 三条不可违反的约定

### ① 状态转移写在程序里，不能靠 LLM 自由写状态

V1.3 原文：**「状态转移写在程序与数据库事务中，不能靠 LLM 自由写状态。」**

实现方式：

```python
rc.transition("approved", actor="李娜(医学审核)")
```

- `transition()` 校验合法转移表，非法直接抛错**并记审计**
- **LLM 不得执行任何状态转移**（`actor` 为 `llm`/`system_auto`/空 → 拒绝）
- LLM 只能*请求*转移，由 `transition()` 判定是否合法、是否需要人工

```
✅ 拦截非法转移：[ILLEGAL_TRANSITION] 非法状态转移：captured → published。当前允许：['transcribed', 'needs_revision', 'rejected']
✅ 拦截 LLM 越权批准：[ACTOR_NOT_AUTHORIZED] 状态转移必须由具名人工执行，不能由 LLM/系统自动执行
```

### ② 两个事实概念必须分开

| 概念 | 问的是 | 独立取值 |
|---|---|---|
| `statement_is_medically_supported` | **医学论断**是否有依据 | 是 / 否 / null |
| `event_occurrence_verified` | **事件发生**是否有佐证 | 是 / 否 |

「医生好像不认可」属于 `inference`：

```
statement_is_medically_supported = False   （主观推测，不是医学论断）
event_occurrence_verified      = False   （无佐证）
```

**绝不因为是 inference 就写成「医生不认可」这种确定性字段。**

**只有 `self_answer`（代表自己的陈述）才可能判为「医学有依据」。**
`reported_question`（医生的提问）、`inference`、`unresolved` 都不产生医学论断 ——
把它们也判成「有依据」会制造虚假的确定性。

### ③ 两条进化路径不可合并

| 路径 | 触发 | 审批 | 影响范围 |
|---|---|---|---|
| **个性化复训** | 员工训练表现 | 无需签审（自动）| 仅该员工 |
| **共享题库更新** | GapCandidate 经审核 | **必须审核发布** | 影响全体 |

实现上**不是二选一**，而是**同一个差异并行产生两个候选**：

```
5 个差异 → 8 个候选
  ├─ 5 个个性化（标识=张伟，状态 auto_assigned）
  └─ 3 个共享候选（★已去标识化，状态 pending_review）
```

**共享层候选去标识化**：`user_id = None`、`source_debrief_id = None` —— 不含任何员工标识，
无法反查是谁提的。**共享层与个人训练层数据隔离。**

## 2. 环节 ① 复盘采集

| 约束 | 实现 |
|---|---|
| 三个主引导问题 | ①对方问了什么 ②我怎么回答 ③我哪里不确定 |
| 来源标记 | 每段必标 `verbatim` / `summary` / `inference`，**三者不可混用** |
| 必填字段 | 原始转写、用户修订稿、发生时间、提交时间、权限范围 |
| 禁入：患者 PII | `病案号`、`住院号`、身份证、手机号、`某先生52岁` → **阻断** |
| 禁入：未授权录音 | 出现「录了一段」且未标授权 → **阻断** |
| 临床不良反应 | **不阻断**，但打引导标记 → 走法定/企业报告路径，本系统不替代 |
| 可撤回性 | `revise()` → 版本 +1、状态回到 `captured`（触发重新解析）、记审计 |
| 事实边界 | 「复盘是代表的报告；本系统只能核验专业知识依据，不能仅凭单人复盘证明一次现场交流的完整真相」 |

**来源标记为什么强制**：混用会让下游把「推断」当成「原话」，
进而把主观推测写成专家的确定性字段 —— 这是 D6「不可见他人错误」之外另一条信息边界。

## 3. 环节 ② 结构化观察

四种 `kind`：

| kind | 含义 | 医学论断判定 | 事件佐证 |
|---|---|---|---|
| `reported_question` | 对方提出的专业问题 | ❌ 不是代表的论断 | 视来源而定 |
| `self_answer` | 代表自述的回答 | ✅ 判定 | 视来源而定 |
| `inference` | 主观推测 | ❌ 不是论断 | 视来源而定 |
| `unresolved` | 未解决的问题 | ❌ 没有论断 | 视来源而定 |

**医学支撑判定复用已有模块，不另起一套**：
FactGuard（合规红线）+ 检索层（库内事实）→ 得出结论与出处引用。

## 4. 环节 ③ 差异分析

### 三级比对（不能只按文字相似度）

| 层级 | 说明 |
|---|---|
| ① 能力点 `skill_id` | 最强证据 |
| ② 医学证据主题 `evidence_topic` | 中等 |
| ③ 提问意图 `intent` | 弱 |

### 五分类

| 分类 | 含义 | 后续路径 |
|---|---|---|
| `covered_mastered` | 已覆盖且掌握 | 无需动作 |
| `covered_not_mastered` | 已覆盖但没掌握 | 补强训练 |
| `not_covered` | 未覆盖（**需训练侧证据**：该能力点没被训到，或复盘中观察到但计划未包含）| 新增考点候选 |
| `partial` | 部分覆盖 | 补强训练 |
| `unknown` | 记录不清，无法判定 | 不做推断 |

**必须随差异结论记录**：`match_evidence`（匹配依据）与 `observation_quality`（样本质量）。

### ★ 一条容易判错的语义

| 情形 | 判定 | 理由 |
|---|---|---|
| 能力点在训练计划里，复盘**观察到了** | `covered_mastered` / `covered_not_mastered` | 掌握与否看训练记录 |
| 能力点**不在**训练计划里，但复盘**观察到了** | `not_covered` | 发现了计划该覆盖但没覆盖的能力 → 新增考点候选 |
| 能力点在训练计划里，但本次复盘**没观察到** | **`unknown`** | ★ **一次复盘没谈到 ≠ 没覆盖** |

第三条最容易判错。早期实现把「计划内但复盘未提及」也判成 `not_covered`，
结果是**一次普通拜访就生成 5 个假的复训候选**。
正确做法是：`not_covered` 需要**训练侧证据**，复盘侧只能给 `unknown`。

**对外表述**：用「**复盘报告的题目覆盖情况**」，不声称"预测了真实医生的言行"。

### 能力点自动匹配（对接 skill-taxonomy）

复盘是自由文本（「是不是获批适应症」），能力点是关键词组织的（「免疫或靶向治疗适用人群」）——
**存在词汇鸿沟**。`SkillMatcher` 用三层信号搭桥：

| 信号 | 来源 | 例 |
|---|---|---|
| **引号核心词** | 能力点名里的「」 | 「价格异议」「拖延的抗拒」「在研与获批的状态边界」|
| **实体名** | 临床库产品/疾病 | 达伯舒、非小细胞肺癌 |
| **受控词表** | keywords / dimensions | 单臂、PD-1、NSCLC |

实测：

| 复盘文本 | 命中能力点 |
|---|---|
| 「达伯舒跟非小细胞肺癌是什么关系」| `SK-K-DABOSHU-PROD-01` |
| 「价格上他不接受，说太贵」| `SK-C-OBJ-01` 处理「价格异议」|
| 「他拖延着不给我答复」| `SK-C-STAGE-RESIST-01` 应对「拖延的抗拒」|
| 「他转换话题岔开了」| `SK-C-STAGE-RESIST-04` 应对「转换话题的抗拒」|
| 「奥利司他片能治非小细胞肺癌吗」| **无**（库外药品不匹配任何能力点）|

**inference 不做能力点匹配** —— 推测不是能力点的表现，挂上去会制造虚假定位。

## 5. 环节 ④ 审核与场景版本发布

状态机（12 节点）：

```
captured → transcribed → user_confirmed → gap_analyzed
   → review_pending → approved/rejected/needs_revision
   → scenario_proposed → tested → published → retired
```

| 规则 | 实现 |
|---|---|
| **审核与发布分离** | `approved` 的出边**不含** `published`；必须经 `scenario_proposed → tested → published` |
| 状态转移不可由 LLM 执行 | `transition()` 校验；`actor` 为 llm/system_auto/空 → 拒绝 |
| 非法转移留痕 | 抛错**并**写审计（含尝试人、尝试状态、允许出边）|
| 版本可回滚 | `published → retired`，原版本保留可回放 |
| 被拒候选 | `rejected` 是终态，无出边，不得进入任何正式训练 |
| 审计 | reviewer、证据链、政策版本、结果、时间、理由全部可查 |

## 6. 怎么用

```bash
# 端到端演示（四环节全跑）
python3 feedback_demo.py

# 自检（44 项，全离线）
python3 verify_feedback_pipeline.py

# 接进训练流程：跑一次训练 + 复盘
python3 medrep_coach.py --user 张伟 --disease D-NSCLC --dim DF --count 2 \
  --answers coach-demo/answers_good.jsonl \
  --feedback feedback_segments.json
```

`feedback_segments.json` 格式：

```json
{
  "scope": "self_only",
  "raw_transcript": "……",
  "user_revised": "……",
  "segments": [
    {"kind": "reported_question", "source": "verbatim",  "text": "他问我……"},
    {"kind": "self_answer",       "source": "verbatim",  "text": "我说……"},
    {"kind": "inference",          "source": "inference", "text": "他好像……"},
    {"kind": "unresolved",         "source": "summary",   "text": "价格没谈拢"}
  ]
}
```

## 7. 已知局限

| 局限 | 说明 |
|---|---|
| **能力点匹配仍是词表法** | 无 embedding，对完全不含已知词的表述会漏判 |
| **样本质量恒为单人回忆** | `observation_quality` 目前只有 `single_self_report` 一个值 |
| **共享层触发条件较严** | 需「全员未覆盖」；实际应引入跨员工聚合统计 |
| **无复盘 UI** | 只有引擎与演示，输入靠 JSON 文件 |
| **未接人工标注回流** | V1.3 §2.4 的标注回流未实现 |
| **无回放 UI** | `ScenarioVersion` 可回滚，但只能通过 API 读 |
