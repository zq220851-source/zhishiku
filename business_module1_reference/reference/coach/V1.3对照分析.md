## 一、必须立刻纠正的 3 处出入

### 出入 1 ｜评分维度命名完全不同 —— 我们用的是旧稿的维度

| | V1.3 文档（1.5 双维能力评估）| 本项目 D3（在跑，基于旧稿）|
|---|---|---|
| 沟通五维 | **问题理解、回答结构、表达清晰、临场应变、情境适应** | 拜访阶段推进、需求探询深度、异议处理质量、表达与节奏控制、合规表达边界 |
| 专业知识四项 | **知识准确性、证据运用、适用边界、专业与合规要求** | 事实准确性、证据引用质量、场景适配性（3 项）|

**影响**：这是评分系统的骨架，命名不同 = 维度定义不同 = 评分基准、rubric、报告口径全线不一致。V1.3 的五维是**能力导向**（抽象、可跨场景复用），我们的五维是**行为导向**（具体、可观测但易与场景耦合）。

**建议**：以 V1.3 命名为准（它是更新版本），但保留我们五维的**可观测性优势**——我们的每个维度都有"典型扣分信号"，V1.3 没有。合并方案：V1.3 命名 + 我们的扣分信号锚点。

---

### 出入 2 ｜题量不该固定 3 道 —— 我们照抄了旧稿

| | V1.3 文档 | 本项目 |
|---|---|---|
| 题量 | **不固定**，由「训练时长预算 + 覆盖能力点数量 + 用户选择 + 模型追问耗时」共同决定；AT03 明确验收"不能固定死 3 道" | 固定 3 题（1 专业 + 1 异议 + 1 压力）|
| 优先级 | 可解释优先级（"为何推荐：与专家研究相关/常见培训考点/员工薄弱项"），**禁止虚构"某专家提问概率"** | 固定配比，无优先级机制 |
| "高频" | D05 列为待拍板："高频"词的统计口径——**容易产生虚假频次宣称** | 直接用"高频问题生成器"这个命名 |

**影响**："高频"这个词在我们的设计里被当成既定概念，而 V1.3 明确说它没有统计样本支撑。**这是最容易在评审会上被打脸的点**——尤其我们还建了一整套叫"高频问题生成器"的模块。

**建议**：①题量改配置策略；②"高频"全系统改称"候选训练考点"，直到 D05 有统计口径；③补可解释优先级（我们的课程映射表已有 `selection_reasons` 雏形，可直接用）。

---

### 出入 3 ｜知识分层的维度错了 —— 我们的"双层"不是 V1.3 的"双层"

| | V1.3 文档（0.2）| 本项目 D5 |
|---|---|---|
| 第一层 | **新信息候选层**：来源索引、论文元数据、研究摘要、前沿资讯、现场回忆与 AI 提炼。**允许带不确定性展示，必须有清晰来源和使用限制** | 语料层（培训课件库）|
| 第二层 | **已审核训练层**：获得授权和专业审批的知识卡、参考答案、题目、评分细则、训练场景版本。**只有这一层可以进入正式评分和标准训练** | 临床层（信达知识库候选，待医学审核）|
| 关键约束 | **日报未审内容不能跳过审批进入正式训练** | 语料层可作"主知识库"（我们 D5 的表述）|

**影响**：我们的"语料层 = 主知识库"表述**越过了 V1.3 的核心约束**。按 V1.3，课件语料属于"候选层"，其角色是训练素材与场景来源，**不能直接当已审核训练层用**。这个差别在合规审查时是要命的。

**建议**：D5 的分级改成三段式——**候选层（语料 + 临床库 + 日报）→ 审核层（ReviewCase 签审）→ 已审核训练层（KnowledgePackVersion）**。我们现有的"来源指纹"设计直接变成候选层的字段定义。

## 二、需要补充的 4 处能力缺口

### 缺口 A ｜板块 02 的核心链路我们只做了 1/5

V1.3 板块 02 的主链是：
```
DebriefRaw → Observation(原话/概述/推测) → GapCandidate
  → ReviewCase → ScenarioDraft → RegressionTests → ScenarioVersion
                                     └→ EmployeeRemediation
```

我们的 D6 只做了**最右侧的可见性与权限**（错误留存不作为处罚依据），而 2.1 复盘采集、2.2 结构化处理、2.3 差异分析、2.4 审核、2.5 版本发布**全都没做**。

**这是最贵的一处缺口**——V1.3 的产品核心价值主张是"训练→复盘→差异→升级场景"的进化闭环，只做训练不做复盘，等于只做了三分之二。

### 缺口 B ｜SkillTaxonomy 与 ExpertRef 完全缺失

V1.3 把 `SkillTaxonomy`（能力点稳定标识）和 `ExpertRef`/`ExpertEvidenceLink`/`TopicAffinity` 列为**共同地基与核心实体**。我们产出里这两个词**零出现**。

- **SkillTaxonomy 缺失**的直接后果：我们的 148 个"知识考察点"是从课程 `scope_items` 切出来的，**不是稳定标识的能力点**。而 V1.3 的 2.3 差异分析（CoverageMap）恰恰要求按能力点比对。
- **ExpertRef 缺失**的后果：V1.3 的 AT01/AT02 要求"只选科室未填专家 → 降级为通用科室训练，绝不捏造专家履历"、"同名作者 → 展示待核实"。我们的 D1 画像卡是**纯虚构医生角色**，完全没有"真实专家学术线索"这一层。

### 缺口 C ｜不可变版本快照与回放

V1.3 要求：`KnowledgePackVersion` 用**不可变快照 version_id** 挂接每一次正式训练，保证回放可复现；一次训练固定 `knowledge_pack_version + rubric_version + scenario_version + role_preset_snapshot` 四个版本。

我们 D3 提了 `rubric_version`，但**没有不可变快照与四版本绑定**。AT11 要求"场景 V2 发布后可显示新增何考点、为何新增、谁审核；支持恢复 V1"。

### 缺口 D ｜日报板块（03）完全没碰

V1.3 板块 03 五个模块（采集/筛选/日报/切入点/知识沉淀）我们一行没做。**但**——信达临床库里的 `harvest_public_metadata.py` 正好就是 3.1 的 SourceConnector 实现（查 PubMed E-utilities + ClinicalTrials.gov），这块有现成起点。

## 三、我们比 V1.3 文档做得更深的地方（应该保留）

| 我们的强项 | V1.3 的状态 | 保留价值 |
|---|---|---|
| **来源指纹字段**（来源类型/版本号/生效日期/审核人/原文定位）| V1.3 只说"要有清晰来源"，没给字段定义 | 我们已定义成可落库结构，直接当候选层字段用 |
| **不可评分剔除 + 知识缺口率** | V1.3 有 `uncertain` 标记与"无证据→待复核"，但没定义**整题剔除且不进分母**的机制 | 我们的规则更硬，能真正防止冤判药代 |
| **语义方向判定（先语境后实体）** | V1.3 完全没提 | 这是合规判定最容易做错的地方，我们领先 |
| **三维处理显式区分**（否决/扣分/不可评）| V1.3 有"硬性风险闸门"概念，无三分模型 | 我们可直接落成代码 |
| **门槛与异常路径**（降级、不伪造、无证据不硬打分）| V1.3 散落在各模块验收里 | 我们集中成表，可直接当验收清单 |
| **可测性矩阵 + 权重重分配公式** | V1.3 只说"缺证据→待复核" | 我们给了完整矩阵与归一公式，可直接实现 |
| **16 个验收场景** | V1.3 给了 AT01–AT16 | 我们缺，但 V1.3 已补齐 —— **直接采用 V1.3 的** |

## 五、工程选型上的冲突

| 项 | V1.3 建议 | 我们实际做的 | 判断 |
|---|---|---|---|
| 多 Agent 并行评分 | "**数据集回归测试比『多 Agent 自我辩论』优先**"、"不建议一期采用复杂多 Agent 自治网络" | D3 用多 Agent 并行按维度评分，P2.6 用多裁判交叉校验 | ⚠️ **超出 V1.3 建议范围**。需说明理由：我们用"每维度独立 Agent + 独立 rubric"是为了维度正交性，不是让 Agent 互相对抗。**但 V1.3 担心的"多裁判无限辩论"确实在我们的 P2.6 里，必须加一致性阈值与人工复核闸门** |
| 数据库 | 演示用 SQLite，多人试点建议 PostgreSQL | 我们的语料用 SQLite + JSONL，临床库用 SQLite | ✓ 一致，但**试点前必须迁 PostgreSQL** |
| 向量检索 | "不是一开始必须，先有可信来源索引和全文/关键词检索" | 我们正是先做来源索引 + 关键词检索 | ✓ 一致 |
| 语音 | ASR→文本编排→LLM→TTS，低延迟实时语音后续做 | D4 形态矩阵按此设计 | ✓ 一致 |
| 前端 | 现有 Next.js + TypeScript 模块化单体 | 未涉及 | 待确认现有代码基础 |
