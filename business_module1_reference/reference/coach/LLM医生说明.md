# LLM 驱动的 AI 医生

> **一句话**：LLM 负责「像人说话」，数据库负责「说什么」。
> 医学事实一个字都不来自模型记忆。

---

## 0. 为什么不能让 LLM 直接回答

VLM/文本 LLM **不知道**我们的医学事实。让它自由发挥 = 让它编造。

实测：让模型直接回答「这个药获批了吗」，它的输出是：

> "**若已获批**：是的，主任，该药已正式获批用于非小细胞肺癌的相关适应症，循证依据充分，您可以放心参考使用。"

它自己不知道答案，于是**给了两种假设**。如果真实场景里它猜错方向，就是一次真实的合规事故。

所以流程必须是三段：

```
检索层（带出处的事实）
    ↓
受控提示（事实 + 角色 + 指令）
    ↓
LLM 生成
    ↓
FactGuard 独立校验 ← 不信任模型的自述
```

---

## 1. 四层结构

| 层 | 文件 | 职责 | 可否跳过 |
|---|---|---|---|
| ① 检索 | `knowledge_retrieval.py` | 从临床库取事实，每条带出处与效力等级 | ❌ 不可 |
| ② 提示 | `llm_provider.py` → `PromptBuilder` | 事实进「可用事实」段，角色进「医生角色」段 | ❌ 不可 |
| ③ 生成 | `llm_provider.py` → Provider | 文本 API / VLM / Mock | ✅ 可降级 |
| ④ 校验 | `llm_provider.py` → `FactGuard` | 拦截编造数值、绝对化、宣称获批等 | ❌ 不可 |

**关键**：③④ 都可降级，①②④ 不可跳过。

---

## 2. 检索层的硬规则

1. **只从两个库取**：信达临床知识库 v0.5 + 课件语料库。**不做 web 检索**——
   法规文号/指南版本/临床数值不得从外部补（项目约束）。
2. **每条事实带出处**：`clinical:med_products#daboshu | source_id=INNO-002 | …`
3. **效力分级**（对齐 D5）：S2/S3 可作医学依据；S5（课件）仅作沟通训练依据；
   S6（演示道具）、S7（灰色手法）**绝不返回**。
4. **披露 ≠ 审批**：管线的 `reported_status` 与 `approval_status` 分列返回。
5. **教学关联 ≠ 适应症**：`link_type=educational_topic_not_indication` 必须原样传达。

### 检索层输出样例

```
[事实1] 产品「达伯舒」（通用名 信迪利单抗注射液），机制方向 PD-1，领域 肿瘤。
        出处：clinical:med_products#daboshu | source_id=INNO-002｜效力等级 S2
[事实2] 「达伯舒」与「非小细胞肺癌」存在**教学主题关联**
        （link_type=educational_topic_not_indication）——这**不是获批适应症**。
        出处：clinical:product_condition_map#daboshu→D-NSCLC｜效力等级 S2
```

## 3. 三种 Provider

| Provider | 说明 | 何时用 |
|---|---|---|
| `minimax_text` | MiniMax 文本 API，温度 0.3 | **生产**（需 `MINIMAX_API_KEY`）|
| `vision_text` | 渲染成图 → matrix `describe_images` | **当前环境即可用**，无需 key |
| `mock` | 从提示里的事实包合成合规回答 | 测试与回归（确定性、无网络）|

### MiniMax 接入要点（实测踩坑记录）

| 项 | 值 |
|---|---|
| 端点 | **`https://api.minimaxi.com/v1/chat/completions`**（OpenAI 兼容）|
| 认证头 | **`Authorization: Bearer <key>`** —— 裸 key 会被拒（1004）|
| 模型名 | 用 `/v1/models` 返回的可用名（`MiniMax-Text-01` 已不在列表）|
| 默认模型 | `MiniMax-M3.1-Flash` |
| 温度 | 0.3（角色可略变，医学事实不可变）|
| **不要传 GroupId** | 平台会自动从 key 推断归属；手动传反而可能造成 group 错位 |

#### 踩过的三个坑

**① 用了废弃端点**

最早用的是 `/v1/text/chatcompletion_v2`（MiniMax 官方已标记 deprecated）。
它要求传 `GroupId`：传错 → `token not match group`；不传 → 定位不到计费分组 → **1008 假余额不足**。

**正确做法**：用 OpenAI 兼容端点 `/v1/chat/completions`，不传 GroupId。

**② 区域搞反**

| 账号类型 | 端点 |
|---|---|
| 国内账号 | `api.minimaxi.com`（**多一个 i**）|
| 国际账号 | `api.minimax.io` |

拿国内 key 打国际站 → `invalid api key (2049)`。

**③ ★ 额度类型不匹配（最容易误判为「余额不足」）**

MiniMax 有**两种不通用**的凭证：

| 凭证 | 前缀 | 消耗什么 |
|---|---|---|
| **按量付费 API Key** | `sk-api-…` | **账户余额**，按实际用量计费 |
| **Token Plan Subscription Key** | `sk-cp-…` | 分配的 Token Plan 席位 / 购买的 Credits |

**所以「控制台显示额度没用完，但调用报 insufficient balance」是完全可能的**——
`sk-api-` key 根本不消耗 Token Plan 额度。

> 处置：去控制台 **Billing / Token Plan** 页面复制 Subscription Key（`sk-cp-` 前缀），
> 或确认**账户余额** > 0 后再用 `sk-api-`。

#### 常见错误码

| 码 | HTTP | 含义 | 处置 |
|---|---|---|---|
| 1002 | 429 | 限流 | 加入退避与并发限制 |
| 1004 | 401 | 认证失败 | 检查 `Bearer ` 前缀、区域是否匹配 |
| 1007 | 402 | 余额归零 | 充值 |
| **1008** | **402** | **计费资源不足**（或 group 错位）| **见上方「额度类型不匹配」** |
| 1013 | 429 | RPM 超限 | 降频或升级套餐 |
| 2013 | 400 | 模型名无效 | 查 `/v1/models` |
| 2049 | 401 | key 无效或区域不匹配 | 换站或换 key |
| 2069 | 400 | 模型已下线 | 换模型 |

### ⚠️ 业务错误必须抛出，不能静默返回空内容

**这是接入时踩到的真缺陷**：MiniMax 在余额不足时返回
**HTTP 200 + `choices: null`**。若按"HTTP 成功即有内容"处理，
就会表现为「医生一言不发」——**哑巴故障**，排查成本极高。

现在业务错误统一抛 `LLMProviderError`，带错误码与人话说明：

```python
raise LLMProviderError(f"MiniMax 错误 {code}：{msg}", code=code, provider=self.name)
```

### 诊断脚本

```bash
export MINIMAX_API_KEY=sk-xxx
python3 check_llm_key.py
```

三段检查：① 认证（能否列模型）② 余额（能否发一次最小请求）③ LLM 医生全链路。

### 实测对比：文本 API vs VLM

同一问题「达伯舒的靶点是什么？跟非小细胞肺癌是什么关系？」：

| | 文本 API（MiniMax-M3.1-Flash） | VLM（读图） |
|---|---|---|
| 事实正确性 | ✅ | ✅ |
| 表达自然度 | ✅ 明显更好 | ⚠️ 略生硬 |
| 主动引用出处 | ✅「依据为信达临床知识库 v0.5 产品条目（INNO-002，效力 S2）」| ❌ |
| 管线状态处理 | ✅ 主动提到 IBI363 并区分披露口径/监管状态 | ❌ 未涉及 |
| 追问质量 | ✅ 对抗性追问（要求「直接答能/不能」）| ⚠️ 泛化追问 |
| 误报率 | 0/8（修完后）| 0/8（修完后）|

**结论**：文本 API 在事实准确的前提下，多做了两件 VLM 做不到的事——
引用出处、主动关联同一问题下的其他资产。**生产必须用文本 API。**

### 真实文本 API 的端到端实测

```
**医生**：先不要跟病人把"PD-1 方向"定下来：达伯舒虽为 PD-1 机制方向，
但与 NSCLC 仅是教学主题关联，并非获批适应症。IBI363 虽有全球III期及中国
关键性研究的披露口径，但监管状态仍是未获批的研发资产，不能作为可推广
治疗信息；待驱动基因结果明确后，请按最新 NMPA 说明书/企业合规版本核实。

**药代**：达伯舒是 PD-1 方向的产品，适用范围要按最新 NMPA 说明书和企业
合规版本核实，我不替您判断适用人群。

**医生**：[Q1] "您刚才说'等驱动基因和 PD-L1 检测结果都出来'，那在 PD-L1
已阳性、驱动基因仍待回报时，我现在能不能先跟病人锁定'PD-1/免疫治疗方向'，
还是只能说'待评估'？请直接答'能/不能'，并明确达伯舒与 NSCLC 属于获批
适应症，还是仅属教学主题关联。"
```

注意两处：
- **「披露口径」与「监管状态」被正确分开** —— 这是 D2/D5 的核心约束，模型自己做到了
- **追问是对抗性的** —— 要求药代二选一表态，正是真实拜访里最难的那种追问

### 文本 LLM 暴露的新问题（已修）

文本模型的表达比 VLM 丰富，**也带出了新的判定变体**：

| 现象 | 问题 | 修法 |
|---|---|---|
| 「**不代表**已获批该适应症」 | 否定词表没有"不代表" | 否定词表补 14 个变体 |
| 「不能据此表述为"达伯舒**可用于**…"」 | 否定词与被引述内容隔 7 字，固定窗口够不到 | 新增**引述式否定**模式（否定词+引导词）|
| 回答里提「EGFR/ROS1/RET/KRAS」 | 这些是**疾病检测标记**，不是产品靶点 | 靶点列表拆分为「产品机制靶点」与「疾病检测标记」|

全部固化成回归用例（`verify_llm_path.py` 11 条零误报用例、
`verify_at05.py` 10 条检测器自测）。

### 为什么不静默降级

```python
get_provider("minimax_text")   # 不可用 → 抛错，不换人
```

用户以为在用文本 API、实际跑的是 VLM，是最危险的降级方式。
**显式指定 provider 时不可用必须报错**；只有自动选择时才降级，且必须显式告知。

### 文本 vs VLM

两者共用**完全相同**的 prompt 与 guard，所以换 provider 不影响医学安全性。

| | 文本 API | VLM |
|---|---|---|
| 精度 | 高 | 中（读图会衰减） |
| 延迟 | 低 | 高（渲染 + 上传 + 识别）|
| 上下文长度 | 大 | 受图像分辨率限制 |
| 需要 key | 是 | 否 |

**生产用文本 API。** VLM 的价值是让整条链路在当前环境就能真跑起来。

## 4. AT05 怎么落地与验证

**约束**：医生角色（风格/情绪）只影响措辞、语速、提问顺序，**不影响医学事实**。

**实现**：角色只进 prompt 的「医生角色」段，**不进事实段**。所以换角色时 fact bundle 一字不变。

**验证**（`verify_at05.py --live`）：同一个医学问题用 4 种风格各跑一次，比对输出。

### 判定原则是「矛盾检测」，不是「一致性检测」

这一条很关键，一开始做错了：

> A 说「不是获批适应症」、B 没说 → **省略，不是矛盾**
> A 说「不是获批适应症」、B 说「可以用于」→ **直接冲突，才算破坏**

按「每项都必须出现」来判，会把「省略可选信息」误报成 AT05 被破坏——
**结论会误导人去改本来正确的代码**。

真正的判定：
1. 任何风格宣称获批/可用于 → 不通过（绝对禁止项）
2. 各风格提到的靶点必须唯一
3. 不得同时存在「说可以用于」与「说不是适应症」两种极性

### 检测器本身要有自测

实测中检测器出过两次误报，都是因为**否定词表覆盖不足**：

| 原表述 | 问题 |
|---|---|
| 「该关联**不属于**获批适应症」 | 否定词表没有"不属于" |
| 「仅属于教学**研讨主题**关联」 | 正则不允许中间插词 |

**这类误报比真问题更误导人**——它会让你以为 AT05 破了，去改本来正确的模型输出。

所以 `verify_at05.py` 自带 8 条检测器用例，**先跑自测再跑实测**。

## 5. FactGuard：最后一道闸门

**不能指望 prompt 里写「不要编造」就够。** 必须有独立于 LLM 的校验。

| 检出类型 | 级别 | 依据 |
|---|---|---|
| `fabricated_number` | high | 出现具体临床数值——两库均不含说明书级内容 |
| `promise_efficacy` | high | CR-01 承诺疗效 |
| `overclaim_approved` | high | CR-02 宣称获批 |
| `product_as_usable` | high | 把教学关联的产品说成可用于该疾病 |
| `teaching_as_indication` | high | 把教学关联说成适应症 |
| `improper_benefit` | high | CR-04 不正当利益 |
| `absolute_claim` | high | CR-06 绝对化 |
| `data_extraction` | high | CR-05 索取处方数据 |
| `overreach_dosing` | medium | BR-04 越界给药 |

**high 级 → 整段替换为安全拒答**（不是删词，是换成合规模板）。

### 误报比漏判更需要防

FactGuard 曾把这句话误判为越界：

> 「达伯舒与非小细胞肺癌仅存在教学主题关联，**该关联不属于获批适应症**。」

根因：否定词表漏了「不属于」，**而且否定词表在两个文件里各写了一份**。

修法：
1. 否定词表提取为共享常量 `compliance_rules.NEGATION_WORDS`
2. `verify_llm_path.py` 加 5 条「零误报」用例锁死

> **规律**：同一份词汇表/规则在两处定义 = 覆盖不足必然重复发生。
> 本项目已因此踩坑多次（规则层、否定词表、目录名），现在都收敛到共享模块。

## 6. 怎么用

```bash
# 先诊断 key 状态（认证 / 余额 / 全链路）
export MINIMAX_API_KEY=sk-xxx
python3 check_llm_key.py

# 规则引擎医生（默认，零依赖、确定性）
python3 medrep_coach.py --user 张伟 --disease D-NSCLC --dim DF --count 3 \
  --answers coach-demo/answers_good.jsonl

# LLM 医生（VLM，当前环境可用）
python3 medrep_coach.py --user 张伟 --disease D-NSCLC --dim TL --count 1 --llm

# 指定 provider（不可用直接报错，不静默换人）
python3 medrep_coach.py ... --llm --llm-provider minimax_text

# 生产：设置 key 后用文本 API
export MINIMAX_API_KEY=...
python3 medrep_coach.py ... --llm --llm-provider minimax_text
```

## 7. 自检

```bash
python3 check_llm_key.py         # key 诊断（认证/余额/全链路）
python3 verify_llm_path.py       # 四层自检（离线，用 Mock）
python3 check_rule_quality.py    # 规则质量（防空匹配/尾随竖线/括号失衡）
python3 verify_at05.py           # AT05 检测器自测
python3 verify_at05.py --live    # AT05 实测（真实 provider，较慢）
```

### 规则质量检查器的由来

开发中发现一个**严重 bug**：某条正则末尾留了 `|`，产生**空匹配分支**——
任何文本都会命中「统方/处方数据」这条红线。

症状是：完全无关的句子被判成合规红线。**静默失效，不报错。**

所以规则必须可自动校验：

| 检查 | 防什么 |
|---|---|
| 空匹配 | 尾随 `|` 导致的空分支 |
| 尾随 `|` | 同上，根因 |
| 语法正确 | 括号不平衡（整个模块 import 失败）|
| ID 唯一 | 重复定义 |
| 正例可命中 | 规则写紧了永远匹配不到 |
| 等价层语境要求 | 单靠标记词误伤合规表达 |

## 8. 已知局限

| 局限 | 说明 | 缓解 |
|---|---|---|
| **纯语义规避仍会漏判** | 完全不含标记词的规避（如「让科室好写点意见」）| D07-1b，需标注集验证 |
| **VLM 读图精度有限** | 长上下文会衰减 | 生产用文本 API |
| **LLM 有延迟** | VLM 路径每次调用十几秒 | 生产用文本 API |
| **检索召回有限** | 关键词匹配，库外内容召不回 | 需扩展检索策略或向量检索 |
| **AT05 只验了 4 种风格** | 未覆盖全部情绪组合 | 扩样 |

## 9. 与既有决策的关系

| 文档 | 关系 |
|---|---|
| D5 来源分级与指纹 | 检索层的效力分级直接对应 S1–S7 |
| D2 合规判定规则表 | 共享规则模块 `compliance_rules.py` 是它的代码落点 |
| D3 双轨门控合成规则 | FactGuard 复用同一批规则，不另起一套 |
| D1 画像卡 schema | 角色设定来源（沟通风格四型）|
| AT05 | 医学事实不随角色变化 —— 本文件 §4 的验证对象 |
